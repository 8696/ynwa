# 用 Skill 让 AI 可靠地操作个人数据库：SQLite + 脚本守门 + 视图收口

> 本文拆解个人助理体系中的四个数据管理子系统——支出记账、待办事项、随手记、资产管理。四个系统共享同一套设计哲学：SQLite 做真值源，Skill 做契约层，脚本做守门人，视图做只读出口。重点剖析 agent 如何可靠地把自然语言翻译成数据库操作，并以记账场景为完整示例。

---

## 一、解决什么问题

用 AI 管个人数据，最大的坑不是 AI 不够聪明，而是 **AI 太自由了**。

直接让大模型写 SQL 操作数据库，会发生这些事：

- **口径漂移**：今天用 `amount` 存美元，明天存人民币，没人发现
- **字段乱填**：`note` 写成"午餐"两个字，丢了地点、金额、评价
- **重复造词**：一会儿"餐饮"一会儿"吃饭"，同义词越攒越多
- **口算汇总**：问"这个月花了多少"，模型心算一个数就报出来了
- **误删误改**：一句"帮我清掉没用的"，DELETE 不带 WHERE 直接扫表
- **半写入**：多步操作中间失败，前一半已 COMMIT，后一半丢了

要解决的，本质上就是这一个矛盾：**大模型有理解自然语言的能力，但没有操作数据库的纪律**。方案不是让模型"更小心"，而是在架构上把"理解"和"执行"分开——模型负责听懂人话、做判断，脚本和触发器负责保证数据库不被写坏。

## 二、整体架构：三层分离

```
契约层  = SKILL.md（路由表 + 铁律 + 禁区）
结构层  = *.sql（表/索引/触发器/视图定义）
数据层  = *.db（SQLite 二进制，运行时真值）
脚本层  = scripts/*.py（agent 与数据库之间的守门人）
引用层  = references/*.md（按需加载的细则文档）
```

**契约层**是 SKILL.md，核心是一张「意图路由表」：

```
| 用户意图          | 只读这个文件                  | 禁止                     |
|------------------|-----------------------------|--------------------------|
| 记一笔 / 花了     | references/quick-insert.md  | 另开文件;夹带清孤儿       |
| 列账单 / 明细     | references/expense-template.md | 当汇总视图用             |
| 花了多少 / 月度   | references/crud-query.md    | 用明细模板凑              |
| 全退             | references/crud-write.md    | 未确认目标笔              |
| 检查异常         | references/anomaly-check.md | 擅自 UPDATE/DELETE       |
```

用户说一句自然语言，agent 按表格命中意图，只读 1 个 reference 文件就动手。不扫全部文档，不做多步推理。这是为弱模型设计的——减少 token、减少决策分支、减少出错面。

**结构层**是独立的 `.sql` 文件，包含完整的 CREATE TABLE / INDEX / TRIGGER / VIEW 定义。git 可 diff，演进可追溯。

**数据层**是 `.db` 二进制文件，直接放在 skill 根目录，不藏子目录。

**脚本层**是 agent 与数据库之间的唯一可信中间人。写操作必须经过脚本，脚本负责参数校验、时间戳、字典查池、标签抽取、健康检查。读操作才允许 agent 直接跑 `sqlite3` CLI 查询——因为只读无副作用。

**引用层**是按需加载的细则文档。SKILL.md 只放路由表和铁律，细节都在 references/ 里，用意图路由表指引 agent 按需读取。

## 三、自然语言到数据库的翻译链路

```
用户口语
  ↓
SKILL.md 意图路由表（命中意图 → 指定读哪个文件）
  ↓
references/*.md 里的 SQL 模板 + 业务规则
  ↓
脚本参数化（防注入 + 校验 + 触发器联动）
  ↓
SQLite 执行（触发器自动补字段/贴标签/刷时间戳）
  ↓
视图读衍生数字（禁止口算）
```

以记账场景为例，用户说 **"下午在公司点了杯咖啡，12块"**，完整链路如下：

### 第一步：意图路由

SKILL.md 路由表命中「记一笔 / 花了」→ 只读 `references/quick-insert.md`。

### 第二步：解析与准备

```bash
python3 references/scripts/prepare_insert.py \
  --amount 12 --when '今天' \
  --item '咖啡' --note '下午在公司点了杯咖啡,12元' \
  --words '咖啡'
```

`prepare_insert.py` 一个脚本做完所有准备工作：

- **日期解析**：`'今天'` → `'2026-08-13'`，反显给 agent，禁止口算
- **normalize**：item/note 文本规范化（全角→半角、多余空格清理）
- **字典查池**：扫描 categories/locations/tags 现有字典，返回可用项
- **标签预检**：`--words` 传入的词与 tags 字典相交，命中自动复用，MISS 打印候选等用户点头
- **查重**：同日同金额同 item 会触发 dup 警告（exit code 2），agent 看到警告后决定是否仍记
- **健康检查**：表/视图/触发器存在性 + 孤儿巡检，一次做完

脚本输出大概长这样：

```
日期: 2026-08-13
categories 现有: 餐饮, 咖啡, 交通, 通讯, 购物, ...
locations 现有: 公司, 家, 线上, ...
tags 已有: 咖啡
tags 缺失(须点头再 INSERT): 无
```

### 第三步：INSERT

```sql
PRAGMA foreign_keys = ON;
INSERT INTO transactions (amount, category_id, happened_at, location_id, item, note, for_self)
VALUES (
  12,
  (SELECT id FROM categories WHERE name='咖啡'),
  '2026-08-13',
  (SELECT id FROM locations WHERE name='公司'),
  '咖啡',
  '下午在公司点了杯咖啡,12元',
  1
);
```

这里有几个关键设计：

- **`category_id` 和 `location_id` 用子查询从字典表取名**，agent 不需要记 id
- **`for_self` 默认 1（自用）**；如果用户说"请同事喝"，agent 自动传 `--for-self 0`
- **最低必填只有 3 个字段**（amount, category_id, happened_at），其余可空——入账门槛低，体检才要求完整

### 第四步：触发器自动联动

INSERT 落库后，SQLite 触发器链自动执行：

```
trg_transactions_after_insert
  ├── note 为空 → 按模板自动生成 note
  ├── 贴标三层：
  │   ├── 1. tag_rules 规则层（keyword 命中 → tag_name）
  │   ├── 2. 字典层（note 子串 ∩ tags 字典，length≥2）
  │   └── 3. 兜底层（分类名 + 地点名自动贴）
  └── 结果：这笔自动贴上「咖啡」「公司」2 个标签
```

tag_rules 规则示例：

```
keyword='咖啡' → tag_name='咖啡'
keyword='午餐' → tag_name='午餐'
```

字典层扫描：note 文本 `"下午在公司点了杯咖啡,12元"` 中，子串 `"咖啡"`（length=2）命中 tags 字典 → 自动建 `transaction_tags` 链接。

**整个过程 agent 不需要手动 INSERT tags**——触发器全包了。

### 第五步：验证 + 报告

```bash
python3 references/scripts/insert_check.py --verify <新id>
```

脚本回显刚插入那笔的完整字段，agent 对照确认后报告给用户：

```
记完了。
id: <新id>
商品: 咖啡
分类: 咖啡
金额: 12 元
时间: 2026-08-13
地点: 公司
自用: 是
标签: 咖啡, 公司
备注: 下午在公司点了杯咖啡,12元
```

## 四、自动标签系统的三层设计

记账系统最有特色的机制是**自动标签**——用户不需要手动打标签，INSERT 触发器自动完成。分三层：

### 第一层：规则层（tag_rules）

人工建的精确规则：

```
keyword='咖啡'   → tag_name='咖啡'
keyword='午餐'   → tag_name='午餐'
keyword='地铁'   → tag_name='通勤'
```

覆盖高频场景。命中即贴，优先级最高。

### 第二层：字典层（tags 字典）

对 note 做子串扫描，跟 tags 字典相交：

- 子串 length ≥ 2
- 排除停用词（"吃了""喝了""买了""今天""早上"等 30+ 个）
- 排除分类名和地点名（避免重复贴）

note `"下午在公司点了杯咖啡"` 中的子串：

```
"咖啡"   → length=2 ✓ → 命中 tags 字典
"公司"   → length=2 ✓ → 命中
"下午"   → 停用词 ✗
"点了"   → 停用词 ✗
```

### 第三层：兜底层

如果前两层都没贴到任何标签，自动贴分类名和地点名。保证每笔交易至少 1 个标签（有专门的触发器强制）。

## 五、四个子系统的关键差异

| | 记账 | 待办 | 随手记 | 资产管理 |
|---|---|---|---|---|
| **核心表** | transactions | items + subtasks | notes | 多账户 × 多业务表 |
| **触发器** | 最多（自动贴标/生成 note） | 少（刷时间戳） | 无（脚本代劳） | 中（同步 subtotal） |
| **视图** | 月度汇总 | 逾期/分类/标签 | 未删列表 | 净资产/占比/信号 |
| **特色机制** | 自动三层贴标 | 周期模板引擎 | 自动标签抽取 | 多币种 + ledger |
| **写入口** | prepare_insert.py | SQL 模板 + 时间解析 | note_db.py | .bail on 事务 |
| **时间精度** | 仅日期到天 | 可到分钟 | 脚本写时间戳 | 精确到秒 |
| **币种** | 单币种 | 无 | 无 | 多币种 |

### 记账：触发器最重

触发器做自动贴标、note 生成、时间校验、退款一致性。agent 只需要 INSERT 一行，触发器链自动完成所有联动。

### 待办：周期模板引擎

周期规则表存模板（每月还信用卡 / 每周写周报），生成脚本判断是否到生成日，自动生成新待办。执行记录表存每次快照。

### 随手记：最轻但自动化不少

一个脚本包了所有写操作。INSERT 时自动从 title+content 抽子串跟 tags 字典相交——命中自动建链接，MISS 打印候选等用户点头。时间由 Python 写入，不走 SQLite（UTC 差 8 小时）。

### 资产管理：最重，做成流水线

把「账户 CRUD」做成了强制流水线 S0→S6，每关有硬门禁：

```
S0 意图分流 → S1 户别路由 → S2 定位(0/1/多分流)
  → S3 写前确认(资金流向必问) → S4 门禁(枚举/ledger/UNIQUE 逐项过)
  → S5 执行(.bail on 事务) → S5b 校验(重查+ledger 硬查)
  → S6 展示(三级展开)
```

大额资金变动必须追问"是从 A 转到 B，还是只更新这一边"，确认后双端同一事务写入。

---

## 六、视图：统一的只读出口

铁律：**衍生数字只查视图，禁口算**。

问"这个月咖啡花了多少"，agent 不心算，跑 SQL 查视图。任何汇总、占比、信号都只能从视图拿，不允许 agent SELECT 原始表再手算。

---

## 七、字典优先：不闭眼造词

所有分类/标签/地点都走字典表，同一条纪律：**先查池，再复用，不够才造，造了要确认**。

防止"同义词分裂"——不会出现一会儿"餐饮"一会儿"吃饭"一会儿"美食"三个分类各记了几笔的情况。

---

## 八、时间处理的取舍

| 系统 | 策略 | 理由 |
|------|------|------|
| 记账 | 仅日期到天 | 不需要精确到分钟；禁止时刻和 ISO 'T' |
| 待办 | 可到分钟 | 有到期时间；自然语言输入走脚本解析 |
| 随手记 | Python 写入 | SQLite `datetime('now')` 是 UTC，差 8 小时 |
| 资产管理 | 精确到秒 | ledger 留痕；汇率按日期存储 |

记账有个专门的时间陷阱：用户上午说"今天下午买了 X"——"下午"还没到，几乎一定是昨天。系统会先查当前时间，发现口述时段尚未到达就先确认日期再落盘。

---

## 九、安全与备份

- UPDATE/DELETE 必须带 WHERE id=?；无 WHERE 批量清空禁止
- 可逆操作不备份；不可逆操作先备份，保留多份
- 改表结构走迁移流程：建新表 → 复制数据 → DROP 旧表 → RENAME，全程事务包裹
- 视图口径变更必须同步 grep 所有依赖：触发器、嵌套视图、报告脚本、文档

---

## 十、总结

核心手段五条：

1. **契约层路由**：SKILL.md 意图路由表，一句话命中一个文件，不扫全量文档
2. **脚本守门**：写操作必须过脚本，脚本做校验、时间戳、字典查池、标签抽取
3. **触发器联动**：INSERT 后自动贴标、生成 note、刷时间戳、校验一致性
4. **视图收口**：衍生数字只查视图，禁止口算
5. **字典优先**：先查池再复用，不够才造，造了要确认

这套模式可以推广到任何"AI + 个人数据"的场景：CRM、健康记录、读书笔记、项目管理——核心都是把"理解"留给模型，把"纪律"交给架构。
